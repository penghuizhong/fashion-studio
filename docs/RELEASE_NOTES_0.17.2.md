# 0.17.2 逐图提示词与图片附件隔离

## 检查结果

上一版主图提示词出现其他任务倾向，确有编排原因：分析系统提示词固定包含主图及卖点规则，自动模板不论数量都附带“同模块多图”说明，最终编译还把全局需求和全部商品资料重复注入各图。逐图请求索引和提示词快照本身未发现互换；本次修正的是内容作用范围及参考图绑定。

没有在提示词中看到网址，并不表示模型没有收到图片。第二步实际发送图片数据URL，第三步按供应商协议发送图片文件或图片数据。内部模特编号无法代替人物图片。

## 第二步到第三步

1. 根据此次选择的图片规划ID，解析其真实商品、细节和模特附件；只读取实际被这些规划项使用的参考图。
2. 识图以JPEG图片数据附件发送，记录来源角色、顺序、源文件SHA-256及识图附件SHA-256。缩放用于识图，图生图阶段继续发送原始文件字节。
3. 各规划项携带自己的模块ID、专用模板、相关资料和绑定图号；系统提示词不再固定注入其他模块规则。全局需求需提取成本项需求，不整段复制进每一项。
4. AI返回的图片ID和模块ID须对应；描述中的分析图号转换为本图实际附件顺序。引用未绑定的图片会报告分析错误，不以其他图片替代。
5. 第三步自动提示词只组织本图任务、商品依据、参考角色、相关摄影风格及必要约束。主图不携带其他模块的品牌、售后或尺码资料，不再重复整段商品规则。
6. 每次生图请求输出1张；用户选择多张时分成多个独立请求。实际模特图片承担人物一致性；内部model_编号从自动描述中移除。未提供模特图片时明确创建新人物。

主图按原图裙摆形态取景，不默认要求额外展开、对称化或增加拖尾。整体设计规范仍可编辑，最终自动编译只采用与本图有关的字段。

## 图片实际发送方式

| 环节/协议 | 实际请求 |
|---|---|
| 第二步识图 | `/chat/completions` 的 `image_url` 内容块，地址为包含实际像素的 `data:image/jpeg;base64,...` |
| OpenAI兼容图生图 | `/images/edits`（或配置的编辑路径），图片通过 `image` / `image[]` 上传，提示词单独放在 `prompt`，`n=1` |
| DashScope多模态生图 | 多模态接口中同一条消息的图片块＋本图文字块，`parameters.n=1` |
| 无参考图的创意生成 | 按协议走文生图；同款商品缺图仍会阻止生成，不静默退化为文生图 |

来源文件路径用于本系统追溯，不要求供应商访问本地路径。公开图片URL不是上传图片文件或图片数据的必要条件。

## 界面与记录

- 需求分析可展开“本次实际识图”，查看实际图片顺序、角色和来源。
- 方案预览每张卡显示：本模块、仅输出1张、图生图/文生图/原图排版，以及商品/细节图和模特图数量。
- 成图记录增加实际调用方式、接口路径、模块、输入图片数和输出数量，继续保存最终提示词与来源摘要。
- 历史手动整段提示词不自动改写，编排规则变化后沿用原有的手稿同步机制；存在旧混合描述的方案建议重新分析。历史任务快照保持原样。
